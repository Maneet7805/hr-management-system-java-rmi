# Phase 3: Database layer design

Status: **Approved by owner. Part 3a merged (PR #7); part 3b built on branch `feature/database-leave-family`** (2026-10-19): `FamilyMemberDao`, `LeaveApplicationDao`, `NewLeaveApplication` and their tests. Phase 3 is complete once 3b is merged.

Part 3b differs from the design in one place: `LeaveApplicationDao` has no `lockById`. `decide` changes the row only while it is still PENDING, in a single statement, so deciding needs no separate lock (a test with two simultaneous deciders confirms exactly one wins). The apply-leave rule (#20) locks the employee row instead, which `EmployeeDao.lockById` already does.

Part 3a contains: settings, `Database`/`DataAccess`/`Work`, the complete schema (all four tables), `SchemaInstaller`, `DatabaseSetupMain`, `EmployeeDao` and `LeaveTypeDao`, and their tests.

Built as designed, with these differences:
- `DataAccess` offers `employees()` and `leaveTypes()` for now; `family()` and `leave()` arrive in 3b.
- Owner decisions: the database user's password is generated by the assistant and kept only in `HRM_DB_PASSWORD`; the database tests fail (not skip) when MySQL is missing, unless `-Dhrm.skipDbTests=true`; length limits are checked in Phase 5.
- `Work<T, E>` carries a generic exception type `E`, so a checked business exception thrown inside a transaction reaches the caller unchanged after the rollback.

## Intent

Give the server a safe, tested way to store and read everything in `DECISION.md` (#19-#36): employees, family members, leave types and leave applications. Phase 3 stops at data access. Login, permissions and leave rules are Phases 4 and 5 and will call this layer.

Why now: the service logic is only as good as the data layer under it, and the leave-balance rule (#19, #20) depends on transactions and row locks that must be proven against a real MySQL, not assumed.

## Goals

- A MySQL schema that enforces the rules itself (unique IC/passport, foreign keys, date checks).
- DAO interfaces the service layer can use, with a fake version for fast tests later.
- Transactions that are explicit and easy to explain, including a row lock for the apply-leave check.
- Every query uses `PreparedStatement`. No string-built SQL.
- Tests run against a separate `hrm_test` database, never the development one.

## Non-goals

- No password hashing, sessions, login or permission checks (Phase 4).
- No leave rules, balance maths or validation messages (Phase 5). The DAO stores and finds; it does not decide.
- No connection pool and no second database type.

## Design

### Reaching the database: `Database` and `DataAccess`

Instead of a hidden per-thread connection, the service asks for a unit of work and receives all four DAOs bound to one connection:

```
database.read(da -> da.employees().findById(7))
database.transaction(da -> { da.employees().lockById(7); ...; da.leave().insert(...); })
```

- `read` opens a connection, runs the work, closes it.
- `transaction` also turns off auto-commit, commits on success, rolls back on any exception, then closes.
- `Database` is an interface, so Phase 5 tests can use a fake without MySQL.

### DAO interfaces (`server.dao`)

| DAO | Methods |
|---|---|
| `EmployeeDao` | `insert(NewEmployee, StoredCredentials)`, `findById`, `lockById` (`SELECT ... FOR UPDATE`), `findLogin(icPassport)`, `findAll`, `updateContact`, `setCredentials` |
| `FamilyMemberDao` | `insert`, `findByEmployee`, `update` (only if it belongs to that employee), `delete` (same rule) |
| `LeaveTypeDao` | `findAll`, `findById` |
| `LeaveApplicationDao` | `insert`, `findById`, `lockById`, `findByEmployee`, `findByStatus`, `findByEmployeeAndYear`, `overlaps`, `daysUsed(employee, year, status)`, `decide` |

Behaviour worth knowing:
- `decide` changes the row only if it is still PENDING, in one statement, so two HR users cannot decide the same application twice.
- `daysUsed` returns days per leave type in one query; the service turns it into `LeaveBalance` (#19).
- Methods that can find nothing return `Optional` or `boolean`, not `null`.
- The password hash and salt live in a server-only record, `StoredCredentials`, and never in the `Employee` the client receives (#36).

### Errors

`DataAccessException` is an unchecked server-internal exception. `DuplicateValueException` extends it for a unique-key clash (for example a second employee with the same IC/passport). Messages never include SQL text or passwords. Phase 5 turns them into `ValidationException` or `ServiceUnavailableException` for the client.

### Schema (`src/main/resources/schema.sql`)

The four tables sketched in `DECISION.md`, plus:
- `ic_passport` unique. MySQL's default collation is case-insensitive, so `a1234567` and `A1234567` clash, which is what we want.
- `leave_application`: checks `end_date >= start_date` and `days = DATEDIFF(end, start) + 1`, so a bug cannot store inconsistent data.
- Leave types seeded: Annual 14, Medical 14, Emergency 3, Unpaid uncapped.
- `CREATE TABLE IF NOT EXISTS` and `INSERT IGNORE`, so running it twice is safe.

`SchemaInstaller` runs that file over JDBC. A small `DatabaseSetupMain` lets you create the tables in your development database.

### Settings

`DbSettings` reads `db.url` and `db.user` from `server.properties` and the password only from the environment variable `HRM_DB_PASSWORD`. The URL keeps the TLS options already in `server.example.properties`.

### Database user

A MySQL user `hrm_app` with full rights on `hrm` and `hrm_test` only, not on the whole server. One user is simpler than separate admin and app users and is enough for coursework; the report can name the split as a future improvement.

## Decisions (assistant calls, owner can override)

1. **Explicit `read` / `transaction` blocks** instead of a thread-local connection. More typing in the service, but nothing hidden to explain.
2. **One connection per unit of work, no pool** (as in the roadmap).
3. **Length limits are checked in Phase 5, not here.** The contract classes accept any length for phone, email and address; the columns do not (30, 100, 255). The service must reject too-long values before they reach MySQL.
4. **`Optional`/`boolean` for "not found"**, unchecked exceptions for real failures.
5. **Database tests skip, not fail, when MySQL or `HRM_DB_PASSWORD` is missing**, so a teammate without MySQL still gets a green `mvn test`. The skip message says why. The cost: a skipped run proves nothing about the database.

## Tests (written first)

Run against `hrm_test`; the schema is installed once and the tables are emptied before each test.

1. **Schema:** installing twice works; leave types are seeded; a duplicate IC (different case) is refused; an end date before the start is refused by the database itself; a family member with no employee is refused.
2. **Employee DAO:** insert and read back; find by IC for login (credentials come back intact); contact update; unknown id returns empty; `lockById` makes a second transaction wait until the first commits.
3. **Family DAO:** add, list, update, delete; an employee cannot update or delete someone else's family member.
4. **Leave type DAO:** the four seeded rows, with Unpaid uncapped.
5. **Leave application DAO:** insert returns the full object; lists by employee, status and year; `overlaps` true for touching and overlapping dates and false for adjacent ones; rejected applications do not count as overlap; `daysUsed` sums per type and year; `decide` works once and the second attempt returns empty.
6. **Transactions:** a failure inside `transaction` rolls everything back; success commits.
7. **No MySQL needed (always run):** `DbSettings` parsing; statement splitting in `SchemaInstaller`; a refused connection gives a readable `DataAccessException` that does not contain the password.
